# Steer 实施与各智能体实测结果（2026-10-14）

本报告记录首批实施时点，产品向 **Codex** 开放公开 Thread 的用户插话。
后续五种 Runtime 接入见[扩展验收](steer-five-runtimes-2026-10-14.md)。多队员按各自状态分别插话、排队或普通发送，
支持附件和纯附件；Agent 消息不进入 Steer。正文继续保存在普通消息中，不建立补充消息库。
以下将原生协议探针与产品验收分开记录，原生单例成功不等于全部竞态或产品接入已通过。

后续原生入口补测和最新汇总见[完整清单](steer-complete-2026-10-14.md)，尤其是 Kimi、Copilot、ZCode、OpenCode 的新增正向证据。

## 实测范围与方法

本机 macOS 26.6 / arm64，共检查 15 类 Runtime，其中 12 类实际启动了原生协议探针。
按 User 要求排除 Cursor、Cline、Command Code。原生探针在实施前执行，基线
`41c8ca19238de8465c23ff0c030f5c7620dd2c02`；使用隔离配置和项目，先运行等待工具，
在可观察工具边界补入中文更正，再检查协议响应、结束顺序及最终标记。
Kiro 未达到工具边界，因此只启动首轮，没有实际提交插话。

原始结构化记录：[逐 Runtime 证据](steer-native-2026-10-14.evidence.json)。其中关于产品尚未接入的
限制描述属于探针执行时点。产品候选另以真实 Core、冻结二进制和独立目录验收，
见 [实施验收索引](../../versions/v1.72/steer-verification.json)。未使用日常 App 的数据目录。

## 产品行为与上下文

普通消息与 Steer 共用动态 Builder、Formatter 和 `RUN_INPUT` 结构，每次只包含本次投递消息。
已排队的普通消息不会被插话顺带取走。新输入刷新队伍、Tasks、Mission 和 Additional Skills，
执行身份、模型、权限、工作区及 Bootstrap 沿用该执行冻结值。提示词只修改已确认的四句 historyHint；
不增加 Steer 标签、额外指导或专用裁剪策略。[紧邻前后对比](../../versions/v1.72/model-context-change-steer-shared-input.md)保留完整文案。

发送时绑定目标 Run 与 execution epoch，原生提交再绑定 Codex turn。
正常完成时，明确未发送或明确被拒绝的消息回普通投递，不显示“执行已结束、消息已排队”提示。
用户取消或执行失败不会因此自动开新轮。超时或断连导致结果未知时不自动重发，
只可核对原生记录中的指定 turn 与原输入；没有正向证据就继续保留未知，迟到回执不复活旧 Run。

## 验证口径与限制

产品真实验收覆盖同轮文本、更正后的输出文件、纯附件、多次输入各自 Manifest、普通队列不被偷取，
以及一次多队员发送中的 Codex 插话、OpenCode 排队、空闲 Codex 直接执行。
真实进程及每次尝试的状态由验收索引记录；失败尝试保留，不用最后一次成功抹掉失败。

| 产品验收尝试 | 实际结果 |
| --- | --- |

| 02 | 两个场景通过；属于最后目标绑定检查前的候选，不替代最终验收 |
